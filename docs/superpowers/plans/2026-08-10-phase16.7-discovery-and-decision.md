# Phase 16.7 Discovery & Decision Document

## What happened

Task 16.7 ("删陈旧 infra 目录") was implemented on 2026-08-10 and **blocked** by the implementer subagent because the plan's invariant — "no live import references to any deletion target in non-deleted code" — is false.

The plan was authored before the dashboard, agent_system, cli, and consistency subsystems grew dependencies on the deletion targets. The first scan counted 835 live references; a deeper scan revealed structural circular dependencies in `infra/__init__.py` itself that the plan did not anticipate.

## The structural problem (the part the original plan missed)

`infra/__init__.py` re-exports several modules that are themselves in the deletion list:

| Line | Statement | Why this blocks deletion |
|------|-----------|--------------------------|
| 4 | `import infra.exports as exports` | `infra/exports/` is a deletion target. |
| 6 | `from infra.creator import *` | `infra/creator/` and `infra/creator_*.py` are deletion targets. |
| 7 | `from infra.studio import *` | `infra/studio/` and `infra/studio_*.py` are deletion targets. |
| 8 | `from infra.prose import *` | `infra/prose/` is a deletion target. |
| 9 | `from infra.project import *` | `infra/project/` is not in the plan's list, but is a transitive consumer of deletion targets. |
| 10 | `from infra.core import *` | `infra/core/` is not in the plan's list, but transitively uses `infra.event_sourcing`. |
| 121 | `from infra.di.layer import Tag, Layer, Runtime` | `infra/di/` is a deletion target. |
| 144-145 | `from infra.event_sourcing.models import ...` and `from infra.event_sourcing.store import ...` | `infra/event_sourcing/` is a deletion target. |

In addition, `infra/exports/events.py` (a deletion target) imports from `infra/event_sourcing/{models,store}` (also a deletion target), and `infra/world_model/links.py` ↔ `infra/subplot/` cross-reference each other — both are deletion targets, so they must be deleted atomically.

**Net effect:** the deletion list as written would break `import infra` itself, breaking every consumer of the umbrella package (dashboard, agent_system, cli, tests). The implementer was correct to stop.

## Realistic options

### Option A — Full refactor (option 1 the user picked on 2026-08-10)

> **Status (2026-08-10): REJECTED.** Multi-week refactor (2-3 weeks) with non-trivial
> risk to load-bearing legacy modules; scope is too large for the Phase 16 hygiene
> goal. The user deferred this work to a future dedicated cleanup phase.

**Estimated effort:** 2-3 weeks of focused work across 6-9 sub-tasks. Some of the work (e.g. `infra/exports/events.py` → `lingwen_storage` migration) is a real improvement; other parts (e.g. rewriting 8 dashboard route files to avoid `infra.studio_registry.active_project()`) is mechanical but voluminous.

**What it would deliver:**
- `infra.studio_*`, `infra.cross_volume.*`, `infra.creator_*` no longer imported by any preserve-list code.
- `infra.consistency/checkers/{pacing,foreshadow}_checker.py` use local types or `infra/agent_system` equivalents.
- `infra/agent_system/{chapter_production_pilot,production_summary,chapter_memory_hook}.py` and `infra/cli/commands/{backfill,cascade,ripple_*}.py` are re-architected to not need `infra.cross_volume`.
- `infra/__init__.py` drops all re-exports of deletion targets.
- `infra/exports/events.py` is migrated to `lingwen_storage` events (or the entire `infra/exports/` package is deleted).
- The full Phase 16.7 deletion list becomes executable.

**Risk:** The agent_system and cli commands re-architecting is non-trivial — `infra.cross_volume` provides ripple-tracking, cross-volume scoring, and backfill that the production CLI uses. The refactor would either (a) lose those features, (b) re-implement them in agent_system, or (c) leave the cli commands broken with a TODO. None of these is a small change.

### Option B — Shrink the deletion list (option 2)

> **Status (2026-08-10): REJECTED.** Only 3 of the 12 deletion targets would be
> safely deletable under this option (`infra/poc/`, `infra/novel-factory/`,
> `infra/di/`). The remaining 9 targets still require refactor work, so this
> option leaves the bulk of the cleanup undone and is not worth a partial pass.

Keep only the deletion targets with **zero** live references and a structurally safe removal path:

| Safe to delete | Reason |
|----------------|--------|
| `infra/poc/` | Only `tests/poc/test_end_to_end.py` references it. Can delete both the dir and the test in one commit. |
| `infra/novel-factory/` | Zero live references found. Safe. |
| `infra/di/` | Only `infra/__init__.py:121` and 2 test refs. Remove the re-export, delete `infra/di/`, update `tests/test_infra_modules.py`. |

Keep (do not delete) everything else: `infra.creator*`, `infra.studio*`, `infra.prose*`, `infra.event_sourcing`, `infra.exports`, `infra.cross_volume`, `infra.story_contracts`, `infra.world_model`, `infra/subplot`, `infra/di` (if option B is taken — see above).

Update plan 16.7 with the shrunken list. Phase 16 Gate G2/G3 still pass.

### Option C — Defer 16.7 to Phase 17 monorepo (option 4)

> **Status (2026-08-10): CHOSEN.** User selected this option. Task 16.7 is
> marked as deferred-to-Phase-17 (not deleted from the plan). The
> `docs/superpowers/2026-08-10-phase16.7-discovery-and-decision.md` companion
> doc was added in the same commit so the Phase 16 gate's link still resolves.

The original Phase 16.7 assumed the legacy infra is "obsolete" because Phase 17 will monorepo-ize the package layout. If Phase 17 also moves `infra/*` to `packages/agent-system`, `packages/agent-storage`, `packages/dashboard-contracts`, etc., then the legacy modules are part of the move (or get migrated as part of the move). Defer 16.7's deletion to whichever Phase 17 task is responsible for splitting `infra/agent_system/` from the legacy `infra/*`.

**Trade-off:** the `infra/` directory stays cluttered for longer, but no risky refactor is undertaken now.

## Recommendation

**Selected: Option C** (user choice 2026-08-10). Rationale:

1. The legacy modules ARE load-bearing — deleting them requires re-architecting user-facing features (cli commands, dashboard routes, agent_system sub-modules) that have nothing to do with the Phase 16 hygiene goal.
2. The hygiene goal (a clean, monorepo-ready package layout) is the explicit purpose of Phase 17. Doing 16.7 now duplicates effort.
3. The other Phase 16 tasks (16.1-16.6, 16.8-16.11) do not depend on 16.7 and can proceed independently.

If the user disagrees, Option B (shrink the list) is a defensible second choice — it cleans up 3 of the 12 deletion targets with minimal risk and lets the rest be deferred.

Option A is not recommended unless the user has explicit bandwidth for 2-3 weeks of focused refactor work.
