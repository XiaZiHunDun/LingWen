## 3. Established Conventions (learned from Phases 100-105b)

### 3.1 Commit message format

**Conventional commits + bilingual context**:
```
<type>(<scope>): <subject>

Phase NN <context>:

- <bullet>
- <bullet>

测试基线不变: 1545 PASS, 0 type errors, 0 build errors.
```

**Types used**: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `build`, `perf`

**Subject length**: ≤ 72 chars preferred; 76-92 chars acceptable (Phase 105a C1-3 used `build(deps): remove ...` at 73-90 chars)

**Body sections**: Phase context, bullet list, baseline test line, optional Refs trailer

**Special cases**:
- ESLint rule changes: `feat(eslint):` or `fix(eslint):`
- knip.json config: `build(ci):`
- Dep removals: `build(deps):` (more accurate than `refactor(cleanup):` for build-affecting changes)
- Doc-only changes: `docs:` (CLAUDE.md, handoff docs)
- Spec/plan-only: `docs(spec):` or `docs(plan):` (per file type)

### 3.2 Phase workflow

Each phase strictly:
1. **Explore** (TaskCreate + verify state)
2. **Brainstorm** (AskUserQuestion with 3 options + user picks 1)
3. **Spec** → user review → commit spec
4. **Plan** (writing-plans skill) → user review → commit plan
5. **Execute** (subagent-driven with 2 reviewers) → commit + push
6. **Optional follow-up** if code-quality reviewer flags MEDIUM+ issues

**Key skills used**:
- `superpowers:brainstorming` — scope decision
- `superpowers:writing-plans` — bite-sized task plan
- `superpowers:subagent-driven-development` — implementer + 2 reviewers
- `superpowers:code-review` — spec-compliance + code-quality reviewers
- `superpowers:test-driven-development` — for ESLint rule tests

## 5. Risk Patterns (encountered)

### 5.1 BLOCK pattern (Phase 99/103/97)

Phase 99/103/97 implementers correctly BLOCKED when scope assumptions turned out wrong:
- **Phase 99**: Spec assumed 9 workflows had version conflicts; 11 did. Implementer caught and amended.
- **Phase 103**: Explore agent's "truly dead" verdict was wrong for 3 of 4 functions (they had test consumers). Implementer BLOCKED, user rescoped, implementer resumed with corrected scope.
- **Phase 97**: Same pattern — initial plan called for 4 truly dead, 3 had test consumers, implementer BLOCKED, user chose down-scope.

**Pattern**: implementer should always verify with grep before deleting; explore agents may miss tests; user rescopes when implementer BLOCKs.

### 5.2 Spec accuracy drift

Specs often had stale numbers/paths (Phase 96 `v13.2 (10)` was actually 33; Phase 105b `binaries` field was actually `ignoreBinaries`). Implementer and code-quality reviewers caught these and either amended spec or noted in commit body.

**Pattern**: spec authors should re-grep before commit; reviewers should verify spec claims against actual state.

### 5.3 Out-of-plan commits

Several phases had out-of-plan commits discovered during implementation:
- Phase 102 C3: moved knip.json from root to `apps/dashboard/` (knip doesn't walk parent dirs)
- Phase 103 spec deviation: pivot to knip.json#ignore for `useWidgetRegistry.js` / `creatorPanelMatrix.js` after live consumers discovered
- Phase 97 rescope: 3 functions kept in barrel due to test consumers

**Pattern**: implementers should document out-of-plan deviations clearly in commit body for reviewer visibility.

### 5.4 Lockfile path (Phase 102.2)

`apps/dashboard/pnpm-lock.yaml` was a stale Phase 17.2 npm-lock artifact. pnpm 9 workspace mode uses root `pnpm-lock.yaml` only. Apps/dashboard lockfile was ignored with warning.

**Pattern**: always verify which lockfile pnpm actually uses in workspace mode (`pnpm install` from `apps/dashboard/` updates root lockfile, not the apps/dashboard one).

### 5.5 pnpm version conflict (Phase 99.1)

`pnpm/action-setup@v4` with `version: 9` conflicts with `package.json#packageManager: "pnpm@9.0.0"`. Both reference the same major version, but the action-setup doesn't accept the implicit `packageManager` source of truth when `version` is also specified.

**Pattern**: always let `packageManager` in package.json be the single source of truth; don't duplicate in CI.

### 5.6 espree limitation on optional chain LHS

`x.value?.foo = 2` (assignment) and `x.value?.foo++` (update) cannot be parsed by espree ("Optional chaining cannot appear in left-hand side"). babel-eslint would handle these, but ESLint's default espree parser rejects them.

**Pattern**: when adding new ESLint rule handlers, expect some test cases to be impossible to express with espree. Document with comment instead of inventing a workaround.
